## 0. 文档使用规则

### 0.1 本文档的定位

本文档回答四个问题：

1. 项目最终要做成什么，哪些玩法和体验不能丢。
2. 项目采用什么技术架构，代码应该放在哪里。
3. 应按什么顺序开发，每个阶段完成到什么程度才算通过。
4. 每次向 AI 编程助手下达任务时，如何约束修改范围、验证结果并避免破坏已有功能。

本文档不是产品需求文档的替代品。产品规则以需求文档 V1.5 为基线；本文档负责把产品目标转化为工程实施顺序和验收标准。

### 0.2 资料优先级

发生冲突时，按以下顺序处理：

1. 已确认的产品决策与最新书面变更记录。
2. 《杭州大富翁》最新版本需求文档。
3. 本开发路线文档中的架构、工程规范和阶段验收约束。
4. 已实现代码。
5. 开发者或 AI 对需求的推测。

**代码当前怎么写，不代表产品就应该怎么设计。** 发现代码与需求不一致时，先登记差异，再决定修正方式。

### 0.3 每次开发的固定流程

任何功能开发都遵循：

1. 阅读本文档，确认当前阶段和对应任务编号。
2. 阅读相关需求章节与现有代码。
3. 明确本次要修改的文件、接口、状态和验收条件。
4. 先给出简短实施计划，再开始改代码。
5. 小步提交，避免一次性重写多个系统。
6. 执行类型检查、构建/编辑器检查和相关测试。
7. 汇报改动文件、实现内容、验证结果、未完成事项和风险。
8. 更新本文档中的任务状态，必要时更新架构决策记录。

没有经过确认，不得擅自扩大任务范围。

### 0.4 任务状态标记

- [ ] 未开始
- [~] 进行中
- [x] 已完成并通过验收
- [!] 被阻塞或存在待确认问题
- [-] 已决定不做

任务只有在代码存在、验证通过、验收条件满足后才能标记为 [x]。仅创建文件或写出空类不算完成。

# 第一部分：产品目标与开发边界

## 1. 项目定位

《杭州大富翁》是一款以 2010—2026 年杭州城市扩张与房地产周期为背景的单机回合制地产经营策略游戏。玩家与三名 AI 对手在不断变化的年轮式城市地图中买地、升级、经营现金流、承担杠杆风险、应对历史事件和政策，最终以净资产决定胜负。

本项目首版目标平台为 H5 独立站。当前开发阶段先完成 Cocos Creator 工程和核心玩法，不在阶段 0 接入广告、账号、云存档或线上服务。

## 2. 核心设计支柱

以下四项是开发过程中不可随意牺牲的产品支柱：

1. **历史即关卡**：时间推进会改变地图、地块解锁、事件、政策和数值。
2. **板块轮动**：区域热度会变化，没有永久强势的区域；玩家需要预判趋势。
3. **现金流博弈**：买地只是开始，租金、利息、物业费、杠杆、冻结和破产共同决定策略。
4. **梗即内容**：杭州城市记忆和事件卡是内容辨识度来源，但真实人物、企业、楼盘等内容须遵循合规和去标识化规则。

## 3. 已确认的产品边界

- 平台：H5 独立站。
- 玩法：单机，1 名人类玩家 + 3 名 AI，不做实时联机。
- 单局：分章战役；玩家可选择章节直接开始，也可连续通关。
- 章节：第一章 2010.01—2013.12；第二章 2014.01—2017.12；第三章 2018.01—2021.12；第四章 2022.01—2026.12。
- 回合：一个回合代表一个月；单骰 1—6。
- 美术方向：二头身平面角色，结合大富翁式棋盘质感。
- 商业模式：纯广告，不做内嵌付费；广告接入不属于阶段 0。
- 首发路径：需求文档确认境外首发方向；域名、发行主体、广告合规等事项在发行阶段另行验收。
- 技术：Cocos Creator 3.8 + TypeScript。

## 4. 开发原则

### 4.1 先做可玩的最小闭环，再扩充内容

优先完成一章可从开始玩到结算的垂直切片。不要先制作大量卡牌、建筑、美术资源或广告功能，再回头拼接玩法。

### 4.2 规则与表现分离

游戏规则、数值计算、AI 决策和回合状态不能依赖动画播放完成。逻辑层先产生确定的结果和动作记录，Cocos 表现层再播放动画。

这样才能支持：

- 跳过动画；
- AI 快速结算；
- 自动模拟和数值平衡测试；
- 回放、日志和问题复现；
- 将来调整 UI 或更换表现方式。

### 4.3 AI 与人类使用同一套规则

AI 不允许使用人类无法使用的特殊结算路径。AI 和人类只能在“决策方式”上不同，购买、升级、贷款、支付、破产等规则必须共用。

### 4.4 配置与程序分离

地块、区域、时代、事件、政策、角色、AI 性格等可调整内容尽量使用配置数据。程序负责解释和执行配置，不要把大批量数值直接写死在业务代码中。

### 4.5 不提前过度设计

阶段 0 不实现完整游戏玩法，不接广告，不做账号系统，不做联网，不制作最终美术。只搭建足以支撑后续开发的工程骨架。

# 第二部分：总体开发路线

## 5. 阶段总览

以下周期是单人/小团队开发的初步估算，不是硬性承诺。阶段验收比日历时间更重要。

| 阶段 | 名称 | 预估周期 | 核心产出 |
|---|---|---:|---|
| 0 | 工程初始化与基础架构 | 1—2 周 | 可运行 Cocos 工程、目录规范、代码规范、基础状态与事件机制、测试入口 |
| 1 | 核心规则与经济系统 | 2—3 周 | 可独立测试的规则内核、地块/经济/回合/章节系统 |
| 2 | 第一章可玩垂直切片 | 3—5 周 | 人类玩家 + 3 AI，从开局到结算的完整一章 |
| 3 | 核心玩法完善与数值校准 | 2—4 周 | 事件、政策、热度、道具、技能、AI、破产、存档稳定 |
| 4 | UI、动画与美术表现 | 4—6 周 | 完整棋盘、角色、建筑、动效、音效、适配 |
| 5 | 内容扩充与完整战役 | 3—5 周 | 四章内容、历史事件、图鉴/财报等扩展内容 |
| 6 | 商业化、合规与发行准备 | 2—4 周（部分并行） | 广告、CMP、隐私政策、部署、监控、发布验收 |
| 7 | 发布后优化 | 持续 | 平衡、性能、留存、内容更新和多语言 |

**建议顺序：** 阶段 0 → 1 → 2 → 3 → 4 → 5 → 6。部分美术资源可以在阶段 2—4 并行准备，但不能阻塞核心规则开发。

## 6. 阶段 0：工程初始化与基础架构


### 6.1 阶段目标

从空仓库创建一个可以被团队持续开发的 Cocos Creator 3.8 + TypeScript 工程。完成后应满足：

- 能在 Cocos Creator 编辑器中打开项目。
- 能运行到一个明确的启动场景。
- TypeScript 脚本能正常编译。
- Git 仓库结构清晰，工程文件和资源可正常协作。
- 代码按表现层、逻辑层、配置层划分。
- 已建立统一游戏状态、事件机制和基础日志约定（不提前实现完整玩法）。
- 有最基本的自动化检查和人工验收说明。
- 新加入的开发者按照 README 可以完成环境准备和启动。

### 6.2 阶段 0 不做什么

以下内容明确不属于阶段 0：

- 不实现完整棋盘移动、掷骰和地块购买。
- 不实现租金、贷款、热度、税务、破产等完整规则。
- 不实现完整 AI。
- 不制作最终角色、建筑和地图美术。
- 不接入 Google 广告、CMP、分析 SDK。
- 不开发账号、云存档、多人联机。
- 不为了“架构完整”预先创建几十个空系统类。

### 6.3 阶段 0 任务清单

#### T0-01：确认开发环境

- [ ] 安装并固定 Cocos Creator 3.8 的具体补丁版本。
- [ ] 安装与项目脚本、工具兼容的 Node.js LTS 版本。
- [ ] 安装 Git。
- [ ] 安装 VS Code 或其他 TypeScript 编辑器。
- [ ] 安装 Cocos Creator 对应的 VS Code 扩展/TypeScript 支持（如需要）。
- [ ] 记录操作系统、Cocos Creator 版本、Node 版本和 Git 版本。
- [ ] 确认团队成员使用同一 Cocos Creator 版本。

**注意：** “3.8”是版本系列，正式协作时应锁定实际安装的 3.8.x 补丁版本，并记录在 README。不要在不同开发者电脑上随意升级编辑器版本。

**验收：** 编辑器可启动；新建的空白 2D 项目可运行；版本信息已写入 README。

#### T0-02：初始化 Cocos Creator 工程

- [ ] 在本地克隆新仓库。
- [ ] 使用 Cocos Creator 创建 2D 项目。
- [ ] 项目根目录直接对应 Git 仓库根目录，避免出现双层同名目录。
- [ ] 工程名称统一为 `hangzhou-tycoon-GPT` 或项目内部确认的名称。
- [ ] 确认启动场景可运行。
- [ ] 将 Cocos 工程必要文件提交到 Git。
- [ ] 不提交编辑器缓存、临时构建产物和本机绝对路径配置。

**推荐：** 使用 Cocos Creator 创建工程文件，不要手工凭空拼装 `settings`、`library` 等编辑器内部文件。

#### T0-03：建立目录结构

建议采用以下结构。Cocos Creator 的资源应放在 `assets` 下；`docs`、`tools`、`tests` 等工程辅助目录放在项目根目录。

```text
hangzhou-tycoon-GPT/

│   ├── scenes/
│   │   ├── Boot.scene
│   │   ├── MainMenu.scene
│   │   └── Game.scene
│   ├── scripts/
│   │   ├── app/                 # 启动、场景切换、全局服务装配
│   │   ├── core/                # 纯规则核心、状态类型、事件类型
│   │   ├── systems/             # 回合、地图、经济、事件、AI 等系统
│   │   ├── data/                # 配置数据类型、加载与校验
│   │   ├── presentation/        # UI、动画、音效、场景表现
│   │   ├── infrastructure/      # 存档、日志、随机数、平台适配
│   │   └── shared/              # 通用类型、常量和小工具
│   ├── resources/
│   │   ├── config/
│   │   ├── localization/
│   │   └── ...
│   ├── textures/
│   ├── audio/
│   ├── prefabs/
│   └── materials/
├── docs/
│   ├── DEVELOPMENT_ROADMAP.md
│   ├── architecture/
│   ├── decisions/
│   └── testing/
├── tests/
│   ├── unit/
│   ├── integration/
│   └── simulation/
├── tools/
│   └── config-validator/
├── .gitignore
├── README.md
└── package.json                # 仅在项目确实需要 npm 工具时维护
```

目录规则：

- `assets/scripts/core` 不应直接 import Cocos 引擎模块。
- `assets/scripts/presentation` 可以依赖 Cocos Creator。
- `systems` 尽量只依赖核心类型和接口，不直接操作节点、精灵或动画。
- 配置文件与运行时状态分开。
- 不要把所有代码都放到一个 `GameManager.ts` 中。
- 不要为了目录好看创建没有职责的空文件。

**验收：** 目录在编辑器中可识别；脚本、场景和资源可正常加载；目录职责已写入 README 或本文档。

#### T0-04：建立代码规范

建议采用以下规则：

- TypeScript 开启严格类型检查；若 Cocos 模板的默认配置存在兼容限制，逐项记录，不要直接关闭所有严格选项。
- 类名使用 PascalCase，例如 `TurnManager`。
- 变量和函数使用 camelCase，例如 `currentPlayerId`。
- 常量使用语义化命名，例如 `DEFAULT_PLAYER_COUNT`。
- 类型和接口使用明确名词，例如 `PlayerState`、`LandConfig`。
- 一个类只承担一个清晰职责。
- 公开函数写注释，说明用途、参数、返回值和副作用。
- 复杂规则必须有单元测试或明确的验收用例。
- 避免无意义缩写、魔法数字和隐式全局变量。
- 不使用 `any` 逃避类型设计；确实无法确定时应在边界处收窄类型并说明原因。
- 不在 UI 组件中计算游戏经济数值。

**建议注释格式：**

```ts
/**
 * 根据玩家当前状态计算净资产。
 *
 * @param player 玩家运行时状态
 * @param landValues 玩家持有地块的当前估值
 * @returns 扣除负债后的净资产
 */
function calculateNetWorth(
  player: PlayerState,
  landValues: number,
): number {
  // 具体实现由经济系统阶段完成
  return player.cash + landValues - player.debt;
}
```

以上代码仅展示注释与命名风格，不要求在阶段 0 实现该业务函数。

   |

- [ ] 创建启动场景 `Boot.scene`。
- [ ] 创建主菜单场景 `MainMenu.scene`。
- [ ] 创建游戏场景 `Game.scene`。
- [ ] 设置正确的启动场景。
- [ ] 建立场景切换入口，避免各个 UI 脚本随意调用场景加载。
- [ ] 初始化失败时给出可读日志，不允许静默卡死。
- [ ] 为后续加载资源预留接口，但暂不建设复杂资源管理器。

**验收：** 从启动场景进入主菜单，再进入游戏占位场景，整个流程可重复运行。

#### T0-06：定义核心类型与 GameState

阶段 0 建立类型骨架，不实现所有字段的业务行为。建议先定义：

- `GameState`：整局游戏状态。
- `ChapterState`：当前章节、起止年月、章节进度。
- `TurnState`：当前玩家、回合阶段、回合编号。
- `PlayerState`：玩家 ID、角色、现金、负债、位置、状态。
- `LandState`：地块 ID、所有者、等级、解锁状态。
- `RegionState`：区域 ID、当前热度和临时状态。
- `ActiveEffectState`：事件/政策等持续效果。
- `GameLogEntry`：可回溯的游戏日志。

建议的概念结构：

```ts
export interface GameState {
  schemaVersion: number;
  chapter: ChapterState;
  turn: TurnState;
  players: PlayerState[];
  lands: LandState[];
  regions: RegionState[];
  activeEffects: ActiveEffectState[];
  logs: GameLogEntry[];
}
```

这只是类型结构示意。字段应结合需求文档逐步确认，避免阶段 0 就将所有未来字段一次性定死。

约束：

- 核心状态不保存 Cocos `Node`、`Sprite`、`Component` 等引擎对象。
- 状态变更必须通过明确的系统方法完成。
- 不允许 UI 直接修改玩家现金、地块所有权等核心数据。
- 状态需要可序列化，为后续存档和回放做准备。
- 为存档保留 `schemaVersion`，未来结构变更必须设计迁移策略。

**验收：** 核心状态类型可编译；可创建一份最小初始状态；不依赖 Cocos 引擎类型。

#### T0-07：建立事件机制与日志机制

建立轻量事件机制，用于逻辑层通知表现层，例如：

- `GAME_STARTED`
- `SCENE_CHANGED`
- `TURN_PHASE_CHANGED`
- `PLAYER_STATE_CHANGED`
- `GAME_LOG_ADDED`

阶段 0 不需要穷举所有事件。事件名应集中定义，避免到处散落字符串。

事件机制约束：

- 明确事件载荷类型。
- 明确订阅与取消订阅的生命周期。
- 场景销毁或组件销毁时应解除订阅，避免重复监听和内存泄漏。
- 事件总线只负责通知，不承担业务规则计算。
- 不要让所有系统通过事件互相隐式调用；关键流程仍应由明确的调度器控制。

日志分级建议：

- `debug`：开发调试细节。
- `info`：正常流程节点。
- `warn`：可恢复异常或配置风险。
- `error`：失败、非法状态或不可继续的错误。

日志应包含必要上下文，例如章节、回合、玩家 ID 和系统名。不要在每帧输出大量日志。

**验收：** 能订阅、触发、取消订阅事件；日志能区分级别；场景重复进入退出不会造成重复回调。

#### T0-08：确定随机数策略

骰子、事件抽取、AI 随机扰动等未来都需要随机数。为了可复现，不能在核心规则中随处直接调用 `Math.random()`。

- [ ] 定义随机数接口 `RandomSource`。
- [ ] 提供可注入的随机数实现。
- [ ] 支持指定 seed。
- [ ] 核心逻辑通过接口获取随机数。
- [ ] 记录本局 seed，便于复现测试局。

**验收：** 相同 seed 和相同输入可以产生相同随机序列；测试可注入固定随机数。

#### T0-09：配置数据边界

配置数据建议采用 JSON 或 TypeScript 静态数据。后续规划的配置包括：

- 地块配置；
- 区域配置；
- 章节/时代配置；
- 历史事件配置；
- 政策配置；
- 机会卡与命运卡配置；
- 角色配置；
- AI 性格配置；
- 文案与本地化配置。

阶段 0 只建立加载与类型约定，不必填充完整数据。

配置原则：

- 配置 ID 稳定且唯一。
- 运行时状态不能直接改写原始配置。
- 缺少必要字段时尽早报错。
- 枚举字段必须校验合法值。
- 数值范围应有校验。
- 配置引用的 ID 必须存在。
- 配置加载失败要能定位具体文件和字段。

**验收：** 可加载一份示例配置；非法 ID 或缺失字段能给出可读错误。

#### T0-10：Git 与协作规范

- [ ] 检查并完善 `.gitignore`。
- [ ] 确认 Cocos 生成的必要元数据按官方工程协作方式处理。
- [ ] 不提交个人编辑器缓存、临时日志和构建产物。
- [ ] 大体积二进制美术资源按实际需要评估 Git LFS。
- [ ] 禁止提交密钥、广告 ID 的私密配置、访问令牌和个人路径。
- [ ] 提交信息使用清晰前缀，例如 `feat:`、`fix:`、`docs:`、`refactor:`、`test:`。
- [ ] 每个功能开发尽量使用独立分支，合并前检查改动范围。

推荐分支：

- `main`：可运行、已验收的稳定版本。
- `develop`：阶段性集成分支（团队协作需要时启用）。
- `feature/<name>`：功能开发。
- `fix/<name>`：问题修复。

单人开发也建议保持小提交，避免一次性提交大量无法定位的问题。

#### T0-11：建立测试入口

阶段 0 需要确定测试方式，而不是提前建设复杂测试平台。

- TypeScript 编译/类型检查；

- Cocos 编辑器内的启动验证；

- [ ] README：项目介绍、环境版本、如何打开、如何运行、目录说明。

## 7. 阶段 1：核心规则与经济系统

### 7.1 目标

先在不依赖最终 UI 和动画的条件下，实现可单元测试的规则内核。阶段结束时，游戏可以在纯逻辑层推进回合、移动棋子、处理地块和经济结算。

### 7.2 推荐开发顺序

#### T1-01：时间与章节系统

- 章节定义与年月推进。
- 章节开始、结束和直接开局。
- 战役模式章节继承规则。
- 每月历史事件检查入口。
- 新地块解锁检查入口。

#### T1-02：地图与地块系统

- 年轮地图与环路数据模型。
- 地块 ID、所属区域、基础地价、等级、所有权、解锁时间。
- 玩家位置与环上移动。
- 正向/反向移动与经过起点的判定。
- 功能格类型。
- 地块相邻与连片判定。

#### T1-03：经济系统

所有经济计算集中管理，建议形成明确函数：

- `calculateLandPrice()`
- `calculateRent()`
- `calculateToll()`
- `calculatePropertyFee()`
- `calculateLoanInterest()`
- `calculatePropertyTax()`
- `calculateNetWorth()`
- `calculateLiquidationValue()`

规则函数应尽量纯粹：相同输入得到相同输出，不直接操作 UI，不直接播放动画。

#### T1-04：交易流水与资金流向

每笔资金变化记录：

- transactionId；
- playerId；
- amount；
- type；
- source；
- turn/month；
- relatedLandId（如适用）。

需要能区分系统注入、玩家间转移、资产买卖、贷款、利息和费用。资金流水是后续平衡测试的基础。

#### T1-05：回合状态机

按需求文档的流程建立回合阶段：

1. 月初结算；
2. 时局播报；
3. 掷骰；
4. 移动；
5. 落地结算；
6. 决策；
7. 回合结束；
8. 月末结算。

阶段切换应有明确入口和非法状态保护。动画是否播放，不得改变规则结果。

#### T1-06：玩家与破产系统

- 玩家初始状态；
- 现金、资产、负债；
- 买地、升级、出售；
- 贷款和偿还；
- 现金不足处理；
- 破产、宽限和资产清算；
- 法拍/接管规则。

#### T1-07：单元测试与数值核对

至少覆盖：

- 正反向经过起点；
- 单骰 1—6；
- 环路边界移动；
- 自有地、空地、他人地的落地处理；
- 升级成本与等级限制；
- 租金、过路费、连片加成；
- 物业费、利息、税务；
- 净资产；
- 现金不足、清算和破产；
- 章节开始和结束。

### 7.3 阶段 1 验收

- 规则层可脱离场景运行。
- 同一输入可以稳定得到同一结果。
- 经济公式有测试覆盖。
- 每笔现金变化可追溯。
- 回合状态不能跳过必要阶段。
- 人类与 AI 未来调用同一套规则 API。
- 需求文档中出现的公式和参数均有来源记录；未确认的矛盾登记为待决策项。

## 8. 阶段 2：第一章可玩垂直切片

### 8.1 目标

完成第一章（2010.01—2013.12）的可玩闭环。暂时允许使用占位美术，但不能使用占位规则。

### 8.2 开发内容

- 开始界面和角色选择。
- 第一章地图及必要地块配置。
- 4 名玩家状态（1 真人 + 3 AI）。
- 掷骰、移动、落地、买地、升级、租金和月末结算。
- AI 基础决策。
- 基础事件/政策触发。
- 破产处理。
- 章节结算与胜负展示。
- 最小存档和中断续玩能力。

### 8.3 AI 最小可用策略

AI 不是随机点击。第一版至少考虑：

- 当前现金安全线；
- 地块预期收益；
- 购买后是否会导致现金过低；
- 是否值得升级；
- 是否需要卖地止损；
- 是否应使用贷款；
- 是否有可用道具或技能（后续阶段加入）。

AI 的决策函数与经济规则分离。AI 只输出行动意图，由统一规则系统校验和执行。

### 8.4 垂直切片验收

- 一章可完整开始、进行、结束。
- 四名玩家都能正常行动。
- AI 不会非法购买、重复行动或卡死。
- 章节结算排名与净资产计算一致。
- 玩家可以中途退出并恢复（如存档已纳入该切片）。
- 单局节奏接近需求文档目标，AI 回合没有明显拖沓。

## 9. 阶段 3：核心玩法完善与数值校准

### 9.1 目标

补齐事件、政策、热度、道具、技能、复杂 AI 和数值模拟，建立可以迭代的平衡机制。

### 9.2 系统开发顺序

1. 板块热度与自然回归；
2. 历史事件与政策效果；
3. 机会卡、命运卡和功能格；
4. 道具系统；
5. 角色主动技能；
6. AI 性格、难度和预测能力；
7. 破产、清算与法拍完整流程；
8. 章节间继承；
9. 自动对战模拟与统计报表。

### 9.3 数值校准

必须支持固定 seed 的自动模拟。建议先跑 100 局，再逐步扩大到 1000 局。

观察指标：

- 各角色胜率；
- 各难度胜率；
- 破产率；
- 净资产中位数、均值和极值；
- 现金与负债分布；
- 杠杆率；
- 玩家间过路费转移；
- 系统注入与系统回收；
- 各区域地块购买率和收益；
- 平均回合时长；
- 道具与技能使用频率。

每次调整经济参数应保留调整前后的模拟结果。不要同时大幅修改多个关键参数，否则无法判断变化原因。

### 9.4 阶段验收

- 主要规则有单元测试。
- 事件/政策的持续时间和结束条件正确。
- 切章不会意外清除仍有效的效果。
- AI 与真人结算路径一致。
- 自动模拟可重复执行并输出统计。
- 数值异常可以通过 seed 和日志复现。

- 动画不会阻塞规则层。
- 快速结算和跳过动画有效。

# 第三部分：技术架构规范

## 14. 总体分层

推荐采用三层结构：

```text
┌─────────────────────────────────────────┐
│ Presentation Layer                      │
│ Cocos Scene / Node / UI / Animation      │
└───────────────────┬─────────────────────┘
                    │ 用户意图 / 结果展示
┌───────────────────▼─────────────────────┐
│ Application & Systems                   │
│ TurnManager / GameFlow / AI / Use Cases  │
└───────────────────┬─────────────────────┘
                    │ 调用规则
┌───────────────────▼─────────────────────┐
│ Core Domain                             │
│ GameState / Rules / Economy / Entities  │
└───────────────────┬─────────────────────┘
                    │ 读取配置 / 持久化接口
┌───────────────────▼─────────────────────┐
│ Infrastructure & Data                   │
│ Config Loader / Save / Random / Logger  │
└─────────────────────────────────────────┘
```

### 14.1 Core Domain（核心规则层）

负责：

- 游戏状态和领域类型；
- 经济公式；
- 移动与落地规则；
- 交易与资金流水；
- 胜负和破产判定；
- 规则校验。

核心层尽量不依赖 Cocos Creator。未来即使调整 UI 或测试方式，也不需要重写规则。

### 14.2 Application & Systems（应用与系统层）

负责组织规则执行：

- 回合状态机；
- 章节推进；
- 玩家行动流程；
- AI 决策调度；
- 事件与政策调度；
- 存档用例；
- 自动模拟入口。

系统层协调核心规则，不直接承担 UI 动画。

### 14.3 Presentation（表现层）

负责：

- 场景和节点；
- UI 展示；
- 棋子移动动画；
- 特效、音效；
- 用户输入；
- 结果演出。

表现层向应用层提交命令或意图，读取状态并展示，不自行计算地价、租金、净资产。

### 14.4 Infrastructure（基础设施层）

负责：

- 配置读取；
- 随机数实现；
- 日志；
- 存档适配；
- 浏览器能力；
- 广告、分析等外部服务（后期）。

## 15. 模块职责建议

| 模块 | 主要职责 | 不应承担 |
|---|---|---|
| GameCore | 核心状态和规则入口 | 场景动画 |
| TurnManager | 回合阶段调度 | 地价公式实现 |
| ChapterSystem | 章节和时间推进 | UI 绘制 |
| BoardSystem | 地图、移动、落点 | 弹窗展示 |
| EconomySystem | 经济公式、现金流、流水 | AI 性格决策 |
| EventSystem | 事件抽取与结算 | 播报动画 |
| PolicySystem | 政策持续效果 | 直接修改 UI |
| PlayerSystem | 玩家状态和行动校验 | 角色动画 |
| AISystem | AI 选择行动 | 绕过规则系统 |
| ItemSystem | 道具使用条件与效果 | 道具按钮样式 |
| SaveSystem | 存档序列化和迁移 | 游戏规则 |
| UIManager | UI 生命周期和弹窗 | 经济计算 |
| AudioManager | 音效和音乐播放 | 回合状态变更 |

模块可以按实际复杂度逐步拆分，不要求阶段 0 一次创建全部模块。

## 16. 关键数据流

以“玩家购买地块”为例：

```text
玩家点击购买
    |
    v
UI 发出 BuyLandIntent
    |
    v
Application 检查当前是否允许购买
    |
    v
Economy/Board 规则校验资金、产权和地块状态
    |
    v
更新 GameState + 生成 Transaction
    |
    v
返回 ActionResult
    |
    v
Presentation 更新显示并播放购买动画
```

关键原则：

- 规则结果先确定，动画后播放。
- 动画播放失败不能撤销已成功的规则结算。
- 同一个行动不能因重复点击执行两次。
- 所有失败结果都应有明确错误码或原因。

## 17. 统一行动结果

建议后续系统统一返回行动结果，而不是在业务代码中直接弹窗：

```ts
export interface ActionResult<T = unknown> {
  success: boolean;
  code: string;
  message?: string;
  data?: T;
  events?: GameEvent[];
}
```

该结构为设计建议，正式落地时应统一错误码、事件载荷和结果数据类型。

## 18. 存档与版本迁移

- 存档必须带 `schemaVersion`。
- 存档只保存必要的运行时状态，不保存 Cocos 节点对象。
- 读取存档后执行结构校验。
- 新版本变更字段时提供迁移函数。
- 无法迁移时应提示玩家并保留原始存档备份。
- 自动存档和手动存档要有明确覆盖规则。
- 保存时机至少覆盖关键回合节点，避免刷新页面造成大量进度丢失。

## 19. 性能与资源规范

- 先满足 H5 可运行，再针对低端移动设备优化。
- 控制纹理尺寸、图集数量和音频体积。
- 避免在每帧执行复杂规则计算。
- 对大量 UI 刷新使用脏标记或批量刷新。
- 棋盘格子和棋子优先复用节点，避免频繁创建销毁。
- 资源加载失败应有占位资源和错误提示。
- 构建后实际检查包体积、首屏加载时间和内存。

# 附录 A：首次开发的推荐执行顺序

本仓库当前从空项目开始，第一次开发建议严格按以下顺序执行：

1. **先确认本地 Cocos Creator 3.8.x 具体版本。**
2. 克隆仓库到本地。
3. 使用 Cocos Creator 在仓库根目录创建 2D 工程。
4. 在编辑器中运行默认场景，确认工程可用。
5. 配置并检查 `.gitignore`，首次提交工程骨架。
6. 创建 `docs/DEVELOPMENT_ROADMAP.md`（本文档）并保留为主路线。
7. 按 T0-03 建立目录结构。
8. 建立 Boot、MainMenu、Game 三个最小场景。
9. 完成 T0-05 启动链路。
10. 再完成 GameState、事件、日志和随机数接口。
11. 最后接入配置校验与测试入口。
12. 通过阶段 0 验收后，开始 T1-01。

**不要一开始就让 AI 一次性生成所有系统。** 对新手和 AI 协作开发来说，小任务、明确边界、每步可运行，是最稳妥的方式。
